project 1: olist pipeline

what i actually built

the vibe

an e-commerce manager gets orders every week and manually combines CSVs to make reports. they're hoping the data is clean. it usually isn't.

i built a system that automatically catches the garbage data BEFORE it reaches the report.

what it does (in 30 seconds)

python pipeline/load.py

that's it. one command does:

  • check if data makes sense (reject the broken stuff)
  • organize into tables (so you can find things easily)
  • load into a database (ready for dashboards)

takes 30 seconds instead of 2 hours of manual work.

the magic: three stages

stage 1: validate — "is this row actually valid or is it garbage?"

  • order delivered before it was purchased? → garbage, reject it
  • customer doesn't exist? → garbage, reject it
  • product has no price? → garbage, reject it

from my test run: 2,012 orders came in, 35 were trash, 1,977 made it through clean.

stage 2: transform — "organize this mess"

  • split into dimensions (who/what/when): customer, seller, product, date
  • split into facts (what happened): orders, items
  • calculate metrics: how many days to deliver? was it late?

why split? because if you keep customer info in every order row, you repeat it 100+ times. change it once in the dimension table, and all 100 orders automatically show the update.

stage 3: load — "put it in a database"

  • create tables with clean data
  • create pre-made views for dashboards

done. dashboard gets trustworthy data.

why this matters (my take)

most people think "validation" is boring. but it's actually the thing that makes reports trustworthy.

when the manager sees "1,977 orders," they don't wonder "are these real?" they just trust it. because they know 173 bad rows were caught and logged.

that's the whole point.

cool things i learned

1. business rules are choices

i decided "price can't be negative" should reject rows. but what if the company intentionally gives refunds as negative prices? suddenly my rule is wrong. so validation isn't obvious — you have to ask the business user.

2. one table vs two tables matters

if i put customer info in every order row, and i need to fix a customer's city, i fix 100 rows. with dimensions, i fix 1 row and all 100 orders automatically get it.

3. definitions have to be consistent

i define "late" as "delivered after promised date." every report uses this definition. nobody invents their own "late." this sounds obvious but it's not — lots of companies have different definitions of the same metric.

the test run (what actually happened)

started: 2,012 orders + 2,495 items + other stuff
validation checked everything:
  - 12 duplicate orders → rejected
  - 10 orders delivered before purchase → rejected (impossible!)
  - 6 orders from customers who don't exist → rejected
  - etc.
result: 173 bad rows caught and logged

ended: 1,977 clean orders + 2,448 clean items in database ✅

if those 35 bad orders had made it to the report, the manager would see wrong numbers. instead, they see clean data. that's the value.

why i built it this way

  • validate first: bad data never reaches the database
  • transform smart: dimensions prevent repetition, facts answer real questions
  • load once: run it weekly, get clean data automatically

no manual work. no surprises. just trustworthy data.
